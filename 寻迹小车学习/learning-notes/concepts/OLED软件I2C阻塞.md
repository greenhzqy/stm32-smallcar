# OLED 软件 I2C 阻塞

## 一句话

软件模拟 I2C 发送数据时 CPU 被全程占用，OLED 刷新一次卡 40ms，电机在此期间收不到新指令。

## 问题

控制循环 5ms 一次。OLED 刷新需要 ~40ms。

```
时间线：
  [✓][✓][✓][✓][    OLED 刷新，电机被晾 40ms    ][✓][✓][✓][✓]
  0   5  10  15                                      55  60  65  70ms
```

40ms = 8 个控制周期。每刷新一次 OLED，连续 8 次无法控制电机。

## 为什么定时器中断解决不了

定时器中断只能解决"**什么时候**刷新"的计时问题。

但"刷新本身要 40ms"是**传输速度**问题——软件 I2C（bit-banging）要求 CPU 手动控制每根线的电平变化（微秒级时序），中途不能被中断打断，否则通信出错。

## 解法层级

| 方案 | 难度 | 效果 |
|------|:--:|------|
| **降低刷新频率**（500ms→1s） | 零 | 卡顿频率降低，但还在 |
| **定时器中断计时** | 低 | 计时更准，但卡顿时长不变 |
| **硬件 I2C + DMA** | 中高 | **彻底解决**，后台传输不阻塞 |

## 软件 I2C vs 硬件 I2C

```
软件I2C（现在）：
  CPU: "我拉SCL……等……我拉SDA……等……"  ← 全程盯着
  每发1字节 ≈ 300μs，CPU什么都不能干

硬件I2C + DMA（未来）：
  CPU: "硬件老哥，帮我发这100字节到OLED"
  硬件: "行，你忙你的"                    ← 后台自己发
  CPU: 继续读传感器、算PID、控制电机      ← 不用等！
```

## 当前策略

OLED 刷新间隔改 500ms（原来是 200ms），减少阻塞频率。等车跑稳了再搞硬件 I2C。
